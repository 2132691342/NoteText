# 19 · 大文件分块编辑、表格编辑与崩溃恢复

## 定位

四件互为补充的事，共同点是「不让用户的文件变成打不开、改不了、丢得掉」：

1. **大文件分块浏览 + 单块编辑**：GB 级文件不再被一刀切拒绝，秒开可浏览；
   需要改动时只解锁当前这一块，写回只替换那块字节；
2. **大表格引擎**：CSV / TSV / JSONL / 顶层 JSON 数组走**记录对齐索引 + 分页取数**，
   1000 万行的表也能秒开、滚到底、跳行、改单格、保存；
3. **XLSX 单元格补丁**：流式解析 + 原地改 XML，**样式与图表原地保留**；
4. **崩溃恢复**：异常退出后找回 30 秒前的未保存内容。

第 2 条是本轮的重点：历史的 CSV 链路在 64MB 处截断，超出后只能看前 2000 行
（`MAX_TABLE_ROWS = 5000` + 前端渲染上限 2000 行），且单元格数量被
`MAX_CELLS_PER_SHEET = 200_000` 静默砍掉——用户以为看全了，其实没有。
那条链路（`read_table_preview` + `DocPreview` 里的表格渲染 + 前端 2000 行上限）
已整体删除：表格现在只有一套引擎、一个网格。详见下文「大表格引擎」。

## 大文件分块（承接 [05 · 文件域](05-file-domain.md)）

### 分档

| 大小 | 行为 |
|---|---|
| ≤ 64MB | 全量读入，正常编辑（`MAX_FULL_READ`） |
| 64MB ~ 512MB | 弹窗让用户选：「普通打开（整篇编辑）」或「分块打开」 |
| 512MB ~ 64GB | 不再询问，直接分块（秒开，可逐块编辑） |
| > 64GB | 拒绝（索引扫描本身要过一遍文件，不承诺无限大） |

阈值常量：`service::file::MAX_FULL_READ` / `MAX_FORCE_FULL_READ` 与前端
`stores/editor.ts` 的 `FULL_READ_LIMIT` / `BIG_EDIT_LIMIT` 两两同值，改一边必须同步另一边。
分块上限在 `service::big_file::MAX_CHUNKED_FILE`。

### 单块写回（`big_file_write_block`）

写回只改一个块的字节区间，三道守护缺一不可：

| 守护 | 实现 | 缺了会怎样 |
|---|---|---|
| 乐观锁 | 重读磁盘那块字节，与 `old_text` 比对，不一致报 `1008` | 别人刚改过的内容被旧编辑盖掉，界面一句提示都没有 |
| 原子替换 | 临时文件写 `before + new + after`，再 rename | 写到一半失败留下半个文件 |
| 不整文入内存 | `copy_range` 用 256KB 定长缓冲搬字节 | GB 级文件写回时先吃掉一份完整副本 |

块内行尾跟随原块（原块里出现 CRLF 就写 CRLF），首块带 BOM 就继续带。
写完重建索引（块大小变了，旧偏移全作废）。

### 块索引（service/big_file.rs）

- **1MB 一块**，边界一律落在换行字节上：受支持编码的换行（0x0A）都不可能是
  多字节序列的后续字节，按它切块不会把字符切半。连续无换行的病态文件在
  1MB+4MB 处硬切（UTF-16 对齐到码元边界）。
- 索引记录每块 `{offset, byte_len, line_start}`；块内换行数在扫描期累计进
  `line_start`，闭块后不单独持有。
- 建索引 = 顺序 `BufReader` 扫一遍，每 8MB 回报一次进度
  （`bigfile:progress` 事件），命令层放 `spawn_blocking`，主线程不付这笔钱。
  用户可取消（`big_file_cancel`，取消位按路径登记）。
- **编码只看头部 64KB 采样**，整份文件按这一个编码逐块解码（与编辑器
  行为一致）；解码失败退有损，给替换符不给「块打不开」。
- 索引缓存在 `BigFileService` 内存表（path → 索引），标签关闭
  （`big_file_close`）时释放。读块前比对 mtime，变了自动重建并报 `stale`。

### 整文查找（`big_file_find`）

分页视图没有完整正文，前端查找不能像 CodeMirror 那样就地扫。
查找因此是**后端按块扫描**：一轮最多读 `budget` 字节。

| 维度 | 取值 | 为什么 |
|---|---|---|
| 起点 | 字节偏移 `from_offset` | 行号要换算回偏移，每轮重算等于每轮重扫文件头 |
| 一轮预算 | 4MB（前端传） | 机械盘上也是毫秒级，用户点一次就有反馈 |
| 命中上限 | 500 条 / 轮 | 再多列表也翻不动；`truncated` 让前端知道还有 |
| 重叠区 | 查找词长度 - 1 | 匹配词被读块边界切开时下一轮还能接上 |
| 换行定位 | 块首行号 + 块内二分 | 命中行的全局行号必须与「跳转到行」一致 |
| 编码 | 按整份文件的编码解码 | 非 UTF-16 一律当 UTF-8 解，GBK 文件的命中位置全是乱的 |
| 文件被改 | 报 `1008` | 边扫边改的命中所指的位置不可信 |

三条实现约束（性能与正确性的关键）：

| 约束 | 实现 | 不这么做会怎样 |
|---|---|---|
| 行号不重扫 | 每块先算出全部行首偏移，命中时二分 | 每条命中都数一遍块内换行，500 条命中 = 500 次全块重扫 |
| 大小写只小写化一次 | 整块 `to_lowercase` 后匹配 | 每条命中都把整块重新小写化，4MB 分配 × 命中数 |
| 按真实编码解码 | `encoding::decode(body, encoding)` | GBK / UTF-16 的位置全错 |

扫描以**整块**为单位推进（命中上限到了也先把整块扫完）：
块内命中被丢弃会让「查找下一个」跳过一段内容。

### 索引扫描：`memchr` 而不是逐字节比较

建索引要顺序扫一遍文件，这是「打开 GB 级文件」唯一不可省的 IO。
扫描本身不能成为瓶颈：

| 维度 | 取值 | 为什么 |
|---|---|---|
| 换行查找 | `memchr` / `memmem`（SIMD） | 逐字节 `for b in buf` 在 1GB 上是几十秒，SIMD 是亚秒 |
| 读缓冲 | 1MB | 足够喂满 `memchr` 又不至于把 L2 冲掉 |
| UTF-16 换行 | 两字节模式 `0A 00` / `00 0A` | 单字节匹配会把高低字节各算一次，行数翻倍 |
| 跨缓冲模式 | 尾部留 `pattern.len()-1` 字节 | 否则恰好切在 `0D 0A` 中间的换行永远数不到 |

实测（release，NVMe）：

| 操作 | 200MB / 233 万行 |
|---|---|
| 建索引（顺序扫一遍） | 63ms |
| 读一块（1MB） | 0.8ms |
| 一轮 4MB 查找 | 1.5ms（命中 500 条即达上限） |

逐字节比较同规模要 4s 量级——「GB 级文件打不开」在多数机器上
不是内存不够，而是这几十秒被当成「卡死」被用户强杀。

### 块内不重复复制

块解码后行尾归一原本无条件 `replace` 两次（CRLF→LF、CR→LF），
每个 1MB 块都要整块拷两份。`normalize_newlines_if_needed` 只在正文含 CR 时才复制：
纯 LF 的块（绝大多数日志 / 源码）直接原样返回。

### 前端（ChunkedViewer.vue）

- 分块标签带 `chunked` 标记（运行时字段，不进会话契约）；EditorArea 优先路由
  到 ChunkedViewer，Minimap 与统计读不到注册表条目时自动降级。
- 块导航条：上一块 / 下一块 / 跳转行（行号先二分到块，再把光标落到块内对应行）。
- 光标换算成全局行号写回标签元数据：块内行 + 块起始行 - 1。
- 会话恢复的大文件标签不持久化 chunked 标记：挂载时 CodeEditor 读文件报
  `1004` 即转分块（自动降级），恢复链路不需要提前 stat。
- **编辑默认关闭**：「编辑本块」解锁当前块（修改 compartment 重配），
  区块变脏时标 `blockDirty`；切块 / 退只读前若未保存，先弹确认。
  Ctrl+S 只保存当前块，与整篇保存完全分开。
- 截断标签（`truncated`，只读了前段）一律只读：保存会把剩余部分删掉，这条护栏沿用 specs/05。
- 外部变更：分块标签不做全量重读，读块时后端按 mtime 报 stale 提示；
  写入时后端做字节级乐观锁，过期报 `1008` 并自动重载该块。

### 取舍

| 选择 | 优势 | 代价 |
|---|---|---|
| std `File + Seek` 分块读，不引 mmap crate | 零新依赖；按需读 1MB 与 mmap 等价 | 每块一次系统调用（微秒级，不可感） |
| 块边界只对齐换行，不对齐编码序列 | 算法一句话说清 | UTF-16 硬切处可能出现一个替换符（病态文件才触发） |
| 只解锁单块编辑，不做全篇编辑 | 写回只替换一个字节区间，数据风险面最小 | 跨块改写要一块一块改（大文件本来不该全篇改） |
| 整文件单一编码 | 与编辑器行为一致，块间不会换编码 | 头部 ASCII 尾部 GBK 的混合文件显示为替换符（强制编码重开可解） |

## 大表格引擎（CSV / TSV / JSONL / 顶层 JSON 数组）

### 定位

**大 CSV 打不开、或者只能看开头几行**，这是表格场景的根本矛盾。
历史上有两条并行的表格链路，前一条（`read_table_preview`：读前 8MB、
`MAX_TABLE_ROWS = 5000`、前端再限 2000 行）就是「100 万行只能看到 25 行」的产物。
那条链路已删除：表格只留一套引擎、一个渲染器。

根因不是「行数太多」，而是**架构把表格当成了「一大段文本」**：
正文整篇进内存、解析在主线程、渲染全量铺 DOM。三件事各自都够呛。

引擎的三个支点：

| 支点 | 做法 | 收益 |
|---|---|---|
| 记录对齐索引 | 块边界落在**记录边界**上，索引是稀疏的 | 内存占用与行数无关（1000 万行 ≈ 几千条索引项） |
| 分页取数 | 一次 IPC 取一页（500 行），滚到哪取到哪 | 前端 DOM 只含窗口内的行 |
| 覆盖层写回 | 改动只存在内存里，保存时**流式重写**整个文件 | 改第 8765432 行的一格，内存占用不变 |

### 三种形态，一套引擎

| 形态 | 判定 | 记录边界 |
|---|---|---|
| CSV / TSV | 扩展名 | 引号状态机（引号包裹、`""` 转义、字段内换行） |
| JSONL / NDJSON | 扩展名或首行是 JSON 对象 | 行 |
| 顶层 JSON 数组 | 文件以 `[` 开头 | 元素边界（可跨行） |

三者共用同一套分页 / 查找 / 写回链路，前端只有一套网格。

### 记录边界扫描器（service/table/records.rs）

**为什么不能按字节找分隔符**：GB18030 / Big5 / Shift_JIS / EUC-JP 的续字节
取值范围覆盖 ASCII 区（0x40–0x7E），一个汉字的尾巴可能被误判成分隔符。

可行的前提是：换行（0x0A）、引号（0x22）、分隔符（`,` `	` `;` `|`）
这几个 ASCII 字节**不是**上述编码的续字节取值，所以字节级扫描是安全的——
它只在这些字节上判断，不解码。

| 扫描器 | 用途 | 特点 |
|---|---|---|
| `RecordScanner<u8>` / `<u16>` | 建索引 | SIMD（`memchr3`）找三类特殊字节；状态跨块延续 |
| `StreamParser` | 写回时流式解析 | 状态跨块延续，引号字段里的换行不会切断记录 |
| `JsonArrayScanner` | 顶层数组 | 跟踪花括号深度与字符串态 |
| `parse_delimited` | 单块解析 | 与 `RecordScanner` 同一套状态机 |

**边界约定必须一致**：字节级扫描与文本级解析切在同一个位置，
否则页边界与索引对不上（读到的行数与索引说的不一样）。

### 索引（service/table/index.rs）

稀疏的两级结构，不是 1000 万条 `(offset, len)`：

| 项 | 取值 | 为什么 |
|---|---|---|
| 块大小 | 1MB | 1000 万行约几千块，索引几十 KB |
| 块边界 | 落在记录边界上 | 记录被切成两半就解析不出字段 |
| 行号 → 偏移 | 块索引二分 + 块内行偏移采样（每 64 条记一个记录起始偏移） | 分页据此跳过目标窗口之前的字节，不再整块全量解析 |
| 编码 | 头部 512KB 采样，整份按它解码 | 样本太小，ASCII 开头的 GB18030 文件会误判；前端传 `'auto'` / 不传才探测 |
| 表头判定 | 首行全为非空非数字文本 → 表头；`table_open` 的 `has_header` 可覆盖 | 启发式会把「首行是文本数据」的文件判错，用户要能纠正 |
| 记录数上限 | 2000 万行 | 再多索引扫描本身失去意义 |
| 进度 | 每 8MB 回报一次（`table:progress`） | GB 级文件要顺序扫一遍 |
| 取消 | `table_cancel` | 同大文件分块 |

末尾没有换行的残余记录同样计入行号（JSON 数组除外——元素以 `,` / `]`
收尾，结尾换行只是格式空白）；不计的话最后一行永远取不到。

### 分页取数（`table_page`）

`table_page(path, start_row, rows)` → 该页的行 + 总行数 / 总列数。

定位方式：块索引二分找到覆盖 `start_row` 的块 → 按块内行偏移采样跳到
目标窗口之前最近的记录起点 → 只解析窗口附近 → 跳过采样零头。
没有采样时一次分页要解析整块（1MB 约 2 万条），有采样后只解析窗口加零头，
快速连续滚动时的每页代价从「整块」降到「窗口」。

### 查找（`table_find`）

先字节级预筛，命中才解析：

| 步骤 | 做法 | 收益 |
|---|---|---|
| 1 | 整块 `to_lowercase` 后 `memmem::find` | 105MB 的表从 4.5 秒降到 77 毫秒 |
| 2 | 命中块才解析成字段，精确定位 (行, 列) | 绝大多数块不含关键字，连解析都不用做 |

### 写回（service/table/rewrite.rs）

**覆盖层 + 流式重写**：改动只存在内存里，文件一个字节都没动。

| 环节 | 做法 |
|---|---|
| 覆盖层 | `行 → (列 → 新值)` 的 BTreeMap + 插入 / 删除行 / 增删列的操作表 |
| 保存 | 顺序读原文件 → 逐记录查覆盖层 → 应用 → 写临时文件 → 原子 rename |
| 内存 | 与文件大小无关（256KB 定长缓冲） |
| 取消 | 覆盖层清空即可，磁盘文件从未被碰过 |

**未改动的记录按原始字节搬运**，不重新序列化：
「打开 → 什么都不改 → 保存」必须字节级不变，否则用户文件里的引号风格、
数字格式会在一次无关的保存里被改掉。

### 虚拟滚动的空间压缩（前端）

Chrome 的元素高度上限约 33,554,428px。1000 万行 × 26px = 2.6 亿 px，
直接映射会让滚动条彻底失效。

| 坐标系 | 含义 |
|---|---|
| 逻辑像素 | `displayRows × ROW_H`，与文件真实行数对应 |
| 滚动条像素 | 压缩后的空间，上限 2000 万 px |
| 显示下标 | 数据行在可见序列里的序号（删除的行不占位，插入的行占位） |

压缩比用 `(scrollHeight - viewport) / maxLogical`：
用 `scrollHeight / logicalHeight` 会让底部差一屏——滚动条到底时
对应的是 `scrollHeight - viewport`，不是 `scrollHeight`。

滚轮按「行」步进（不受压缩影响），拖滚动条时按比例换算回逻辑位置。

#### 窗口定位与视口高度（四处必须写对的地方）

这两处合起来就是「100 万行的表只显示 25 行、而且滑不动」的全部原因：

| 环节 | 正确做法 | 写错的后果 |
|---|---|---|
| 滚动容器绑定 | 模板 ref 必须叫 `scrollHost`（`useTableGrid` / `useSheetGrid` 读它量高度） | 名字写成 `scrollEl` 时 `viewport = 0`，`windowEnd = ceil(0/26) + 25 = 25`，且 `onScroll` 首行就 return |
| 窗口顶边 | `scrollTop - (firstVisible - windowStart) × ROW_H`（**滚动条压缩坐标**） | 用逻辑坐标时上亿像素会把窗口推出容器外，滚到中途一片空白 |
| 视口为 0 时 | 给 `FALLBACK_VIEWPORT`（600px）兜底行数，量到真高度即收敛 | 直接按 0 算，只剩 overscan 那几行 |
| 表头偏移 | `computeGridWindow` 的 `topOffset` 传吸顶表头高度；逻辑高度与滚动空间都要算上它 | 数据窗口从内容 y=0 起画，被不透明 sticky 表头盖住，**前两行只有滚动后才露出** |

滚轮与滚动条事件必须 rAF 合帧：高分屏 / 触控板上每秒几十次事件，
不合并就是每秒几十次全窗口 DOM patch——渲染跟不上拖动速度的直接原因。

三条都是「不报错、只是少画」的静默故障，所以由
`frontend/scripts/check-grid-window.mjs`（`npm run check:grid`）机械守护：
它把坐标系算一遍并断言窗口行数正常且始终落在 `[0, scrollHeight]` 内。

### 前端（SheetEditor.vue / useTableGrid.ts）

- 网格按页取数，页缓存放在 `shallowRef<Map>` 里（整体替换，不做深度响应式），
  上限 80 页、LRU 淘汰（来回拖动时刚看过的页不会被误丢；开着大表不无限吃内存）。
- 预取前后各 3 页；滚轮与滚动条事件 rAF 合帧（一帧之内只应用最新状态）。
- 覆盖层同样用 `shallowRef` 持有：几千个改动塞进 Vue 响应式会卡死。
- 单元格编辑：点击进入输入，Enter 提交、Tab 提交并右移、Shift+Tab 左移、
  ↑/↓ 上下移、Esc 取消；非编辑态下方向键移动焦点格、Enter / F2 进编辑。
- 表头两层吸顶：列字母行常驻，`has_header` 时再叠一层表头值行。
- 列宽可拖拽，双击列分隔线按已缓存内容自适应；宽度来自后端 `col_widths` 采样
  （前 200 条记录里每列最长字段，中日韩按 2 个半角算），用户拖过的落前端覆盖层。
- 右键菜单：复制单元格 / 复制整行（TSV，粘进 Excel 直接分列）/ 插入行 / 删除行 / 复制列名。
- **CSV / TSV 没有「只读预览」这个形态**：预览只能截一部分行，而网格本来就能看全部。
  `EditorArea` 对 `isTableGrid` 的标签直接路由到 `SheetEditor`，不走 `DocPreview`。
- 保存走**表格适配器**（`registerTableProvider`）：正文不在内存里，
  保存走后端的流式写回；Ctrl+S / 退出确认 / 崩溃快照复用同一条链路。
- 表格标签的编码默认 `'auto'`：交给后端探测。预设 `'utf-8'` 会让探测永远不生效，
  GB18030 的 CSV 整表解成替换符。状态栏「按编码重新打开」对表格标签走
  `TableProvider::reopen`——按新编码重建索引，不走全量读。
- 「首行作为表头 / 数据」按钮切换 `has_header` 覆盖并重建索引：
  启发式把「首行全是文本」判成表头，首行其实是数据时用户在这里纠正。

## XLSX 单元格补丁

### 范围

| 格式 | 读取 | 保存 | 走哪条路 |
|---|---|---|---|
| XLSX / XLSM | 流式解析（`workbook_info` 摘要 + `sheet_page` 分页） | 原地改 XML（`save_workbook`） | `WorkbookEditor` 网格，真可编辑 |
| XLS（BIFF）/ ODS | 预览器（前端 SheetJS） | 不能原地改 | `DocPreview`，“另存为 xlsx” 后可进网格 |

Excel 单表上限是 1,048,576 行、16,384 列（OOXML 规范），超出部分任何工具都读不了。
打开时按这个上限提示，不静默截断。

**XLS / ODS 为什么不进网格**：后端的写回是「拆 OOXML 的 zip 部件 → 只改命中的 `<c>`」，
XLS 是 BIFF 二进制结构、ODS 是 `content.xml` + 另一套命名空间，两者都没有对应的补丁路径。
强行把 ODS 交给 `workbook_info` 只会得到一句「工作表部件缺失」——
那是内部词汇外泄，不是错误提示。所以两者走只读预览，
并给一条明确的出路：**“另存为 xlsx”**（`write_binary` 命令 + SheetJS 生成字节），
转成 xlsx 后就能进网格改单元格。

`utils/fileKind.ts` 的三个判定函数是唯一路由依据（`isWorkbookSheet` / `isReadonlySheet` / `isTableGrid`），
不在组件里再判一次扩展名。

### 流式解析（service/sheet/stream.rs）

整块解析（`xml.split("<row")`）在百万行的工作表上要吃掉几百 MB 内存。
拉模式解析（`quick-xml`）一次只持有一行，内存占用与表大小无关。

**工作簿缓存**（`service/sheet/mod.rs`）：zip 条目是压缩流，没法在解压数据里
seek——分页要快就得把解压后的 sheet XML 留在内存里。按路径缓存：

| 缓存项 | 内容 | 为什么 |
|---|---|---|
| 文件字节 | 整个 xlsx 的原始字节（`Arc<Vec<u8>>`） | 每页重建 zip 视图只读中央目录，不再重读磁盘 |
| 共享串表 | `Vec<String>` | 一次解码，全表共用 |
| 行偏移采样 | 每 100 行记一个 `<row` 字节偏移（memmem 扫解压 XML，顺带拿总行数） | 分页跳过目标窗口之前的字节；切片缺打开标签时补 `<worksheet><sheetData>` 壳 |
| 常驻 XML | 最近用的一张表的解压 XML（上限 256MB，超限每页现解压） | 翻页不再解压全表；切换工作表时替换，不按表数累积 |

缓存按 mtime + size 判失效，文件被外部改过就整份重建；条目上限 8 个。
没有这套缓存时每翻一页都是 O(文件) 的活（重读磁盘 + 解 zip + 全表扫 XML），
大工作簿的滚动比 CSV 慢一个量级。

| 命令 | 职责 |
|---|---|
| `workbook_info` | 工作表摘要：表名、行列数、是否有公式（不读单元格） |
| `sheet_page` | 分页读取一张表：只构造窗口内的单元格 |

### 写回：为什么是「原地改 XML」

整本反序列化再重新生成工作簿，会把解析链不认识的部分全丢掉：样式表、主题、条件格式、
图表、图片、数据校验。用户看到的是「改一个格，颜色全没了」。

所以 `service/sheet` 走外科手术（契约在 `domain/sheet.rs`，入口在 `commands/sheet.rs`）：

```
读：xl/workbook.xml + rels → 表名与部件路径 → sharedStrings.xml → 逐表解析 <c>
写：解压 → 只替换目标表里被点到的那几个 <c> → 其余部件字节级原样搬回
```

| 守护 | 实现 | 缺了会怎样 |
|---|---|---|
| 样式不丢 | 改值时保留原 `<c>` 上的 `s=`（样式索引）；`styles.xml` 整块原样搬运 | 改一格，字体 / 填充 / 边框全丢 |
| 未编辑的表不动 | 只重写命中的 `sheetN.xml`，其余工作表字节级原样 | 「在 A 表改 A、在 B 表改 B」把 B 的改动写到 A 里 |
| 共享串追加 | 新文本追加进 `sharedStrings.xml` 并重写该部件；已有下标不变 | 已有单元格的值全变 |
| 备份 | 写前把原文件复制成 `.bak`，用户可回退 | 改错了没法退 |

守护测试：`sheet_opens_pages_edits_and_preserves_styles`
（手搭一个带 `s=` 的 xlsx，改完断言 `styles.xml` 与未编辑工作表字节级不变）。

## 崩溃恢复

### 机制

| 环节 | 实现 |
|---|---|
| 标记 | `AppConfig.last_exit_clean`：启动（`app/lifecycle.rs on_ready`）置 false，干净退出（`mark_clean_exit` 命令，前端在 `forceQuit` 前调）置 true |
| 快照 | `useCrashGuard`：每 30 秒把**脏标签**正文静默快照进草稿库（`saveDraft`），内容没变不重写；>2MB 跳过（草稿库上限同值）；分块 / 截断标签跳过（没有完整正文） |
| 识别 | 启动后 `last_exit_clean === false` 且草稿非空 → askPick 提示「打开草稿箱 / 忽略」 |
| 恢复 | 草稿箱（DraftsDialog）逐条决定；快照只进编辑器不落盘，**文件永远不被自动覆盖** |

### 与「源文件旁交换文件」方案的取舍

快照进草稿库而非源文件旁的交换文件：不污染用户目录、天然享受草稿箱 UI 与
备份导出。代价是恢复要用户手动保存一次——这是刻意的：替用户覆盖文件
本身就是一次数据风险。

### 取舍

| 选择 | 优势 | 代价 |
|---|---|---|
| 30 秒间隔快照 | 崩溃窗口最多丢 30 秒 | 每 30 秒一次草稿表写入（脏标签通常 0~3 个，毫秒级） |
| 快照进草稿库 | 零新存储形态，草稿箱 UI 直接复用 | 恢复后要手动保存一次 |

## 约束

- 大文件阈值常量前后端两两同值（64MB / 512MB），改一边必须同步另一边；
  分块上限 `MAX_CHUNKED_FILE`（64GB）只在后端。
- 崩溃快照上限 2MB 与 `repo/draft.rs::MAX_DRAFT_BYTES` 同值。
- 表格索引记录数上限 2000 万行（`service::table::index::MAX_TABLE_RECORDS`）。
- 表格查找单轮命中上限 5000 条；5 万条查找结果封顶。
- 前端滚动空间上限 2000 万 px（`useTableGrid.ts` 的 `MAX_SCROLL_PX`），
  远低于 Chrome 的元素高度上限。
- XLSX 写回只改单元格值与公式；合并单元格 / 列宽 / 行高不在编辑范围内
  （读出来供展示，写回时原样保留）。
- 错误码 `1007 BIG_INDEX_CANCELLED` / `1008 FILE_STALE`：`pkg/error.rs`、
  `assets/specs/15-error-codes.md`、前端 `errCode` / `next` 三处同步。
- 崩溃恢复标记在 `forceQuit` **之前**落库：退出流程中断在标记之前，
  下次启动会多问一次恢复——宁可多问，不可丢内容。

## 关键流程

```
打开 >512MB 文本文件
  openPath → 大小 > 512MB → openChunked → ChunkedViewer 挂载
    → big_file_open（spawn_blocking 扫描，进度事件，可取消）
    → big_file_block(0) → CM 只读视图渲染
跳转行 N
  big_file_goto_line(N) → 二分到块 → loadBlock(idx) → 光标落块内对应行
改一个块
  点「编辑本块」→ 解锁只读 → Ctrl+S 或「保存本块」
    → big_file_write_block（乐观锁比对 → before+new+after → rename）
    → 重建索引 → 块数 / 总行数刷新

打开 1000 万行 CSV
  openPath → 扩展名是 csv → 建标签（不读正文）→ SheetEditor 挂载
    → table_open（spawn_blocking 建索引，进度事件，可取消）
    → table_page(0, 500) → 首页数据
滚动到第 500 万行
  滚动条按压缩比换算 → 逻辑位置 → 二分到块 → table_page(start, 500)
改第 8765432 行的一格
  单元格提交 → 覆盖层记一笔（文件未动）→ 格子变黄
  Ctrl+S → 表格适配器 → table_save（流式重写整个文件）
    → 未改动的记录原样搬运 → 改动的行重新序列化
    → 临时文件 → 原子 rename → 重建索引
查找
  输入关键字 → table_find
    → 整块 to_lowercase + memmem 预筛 → 命中块才解析
    → 命中 (行, 列) → 滚到那一行

XLSX 保存
  单元格提交 → pending 累积（按工作表分组）→ 点「保存工作簿」
    → save_workbook（补丁目标 sheet XML → 重建 zip → .bak 备份 → rename）

崩溃恢复
  异常终止（last_exit_clean 停在 false）
  → 下次启动 → 恢复会话 → 检测 false + 草稿非空 → askPick → 草稿箱
```
